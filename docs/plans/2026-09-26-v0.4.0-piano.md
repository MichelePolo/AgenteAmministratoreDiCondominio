# Piano 0.4.0 — Esperienza d'uso

Spec: [`docs/specs/2026-09-26-v0.4.0-esperienza-uso.md`](../specs/2026-09-26-v0.4.0-esperienza-uso.md)

Ordine guidato dalle dipendenze: il foglio `Rate` e il calcolo `situazione` servono a F1, F2 e
F4, quindi vengono per primi. Un commit per fase; ogni fase lascia il plugin funzionante e con i
test verdi. Percorsi relativi a `plugins/amministratore-condominio/` salvo `tests/`, `docs/` e
`build.sh`, che stanno alla radice del repo e non entrano nel `.plugin`.

Legenda: 🧑 = parte scritta dall'utente (scelta di dominio), ✅ = criterio di fine fase.

## Fase 0 — Test e rete di sicurezza

1. Solo `unittest`, niente pytest (nessuna dipendenza oltre openpyxl): `tests/helpers.py` crea una cartella temporanea con `crea_registro.py --esempio` e offre
   `run(script, *args) -> (codice, json)`.
2. `tests/test_registro_attuale.py`: fotografia del comportamento 0.3 (`verifica` sui dati di
   esempio, `append`/`update` Versamenti → `Saldo`, riparto dei dati di esempio a somma esatta).
   Servono a garantire che il refactoring non cambi niente.
3. `tests/test_nessuna_formula.py`: scorre ogni xlsx prodotto e fallisce su celle che iniziano
   con `=`.
4. `build.sh`: `python3 -m unittest discover -s tests` prima dello zip.

✅ `./build.sh` passa con i test 0.3.

## Fase 1 — Fondamenta in `registro.py` (F0)

2. Estrarre `verifica(wb) -> (problemi, avvisi)`; `cmd_verifica` diventa un involucro.

4. `_refresh`: `Dovuto` da `Rate` (solo se ci sono righe valide per unità/esercizio), `Scaduto`.

7. Test: `tests/test_situazione.py` (pagata, parziale, scaduta, registro 0.3 senza `Rate`),

## Fase 2 — Approvazione deterministica: `riparto.py approva`

1. Sottocomando `approva` (il comando attuale resta il default, per non rompere la skill 0.3).
   Legge `Riepilogo` dal prospetto (intestazioni `ID unità`, `Rata N`, `Totale dovuto`).
2. Controlli: il file esiste ed è `_bozza`; il numero di scadenze coincide; il nome di
   destinazione è libero; `--sostituisce` punta a un prospetto con righe in `Rate`.
3. Scritture in quest'ordine: riservato (`Rate`, `Situazione`) → condiviso (`Scadenze`, Diario)
   → rinomina del file per ultima. Idempotenza: se `Rate` ha già righe per quel `Prospetto`,
   uscire con `ok: false` e spiegare.
4. `riparto/SKILL.md` §4: sostituire i comandi manuali con `approva`; chiedere all'utente le date
   delle rate (non inventarle, come già dice `scadenze`).
5. `tests/test_approva.py`: i casi dei criteri di accettazione (16 righe, somma al centesimo,
   seconda esecuzione rifiutata, `--sostituisce`).

✅ Il flusso "riparto → approvato" del tutorial funziona con un solo comando.

## Fase 3 — Foglio `In breve` (F3)

1. `registro.py`: `_in_breve(wb, cartella)` chiamata da `_save` sul registro condiviso; crea il
   foglio se manca, lo svuota e lo riscrive, lo sposta in posizione 0 e lo rende attivo.
   Formato: colonna A 28, colonna B 42, testo a capo, sezioni in grassetto con sfondo `HDR_FILL`.
2. 🧑 **Scelta dei contenuti e delle parole**: nella funzione `_in_breve` la lista delle sezioni
   (ordine, etichette in italiano, quante righe per sezione) è lasciata all'utente. È ciò che il
   condomino legge per primo dal telefono. Lo scheletro prepara i dati: prossime scadenze, spese
   per tabella, ultimi archiviati, conteggio inbox.
3. `KV_SHEETS`/nuovo `GENERATED_SHEETS = {"In breve"}`: esclusi da `info` (conteggi), `read`,
   `append`, `update`, con un messaggio chiaro.
4. `schema`: crea `In breve` e lo porta in testa.
5. `LEGGIMI.txt` punto 2; `modello-dati.md`.
6. `tests/test_in_breve.py`: primo foglio e attivo; nessun intestatario, email o ID unità nelle
   celle; si aggiorna dopo `append Spese`.
7. **Verifica manuale su telefono** (app Google Drive), con screenshot allegato alla PR.

✅ Test verdi e verifica da telefono fatta.

## Rischi

| Rischio | Mitigazione |
|---|---|
| `Scaduto` cambia con la data ma il file si salva solo alle operazioni | `In breve` non lo mostra; nel riservato la data di `Ultima elaborazione` dice quando è stato calcolato; `stato` ricalcola sempre |
| Import tra skill (`sys.path`) fragile se Cowork copia le skill separatamente | fallback esplicito: se l'import fallisce, messaggio in italiano con il percorso atteso; test che eseguono gli script dalla loro cartella reale |
| Il modello legge male un PDF bancario | l'abbinamento è comunque mostrato e confermato; importi e date del JSON vanno ricontrollati riga per riga nella proposta |
| Foglio `In breve` modificato a mano da qualcuno | viene rigenerato al salvataggio successivo; il testo in testa lo dice |
| Dati personali nel Diario pubblico | regola in `condominio-base` + criterio di accettazione |

## Stima

Fasi 0–3: il grosso del lavoro sugli script (circa 400 righe tra codice e test). Fasi 4–6: una
skill nuova ciascuna, con uno script piccolo. Fase 7: documentazione. Tre punti 🧑 da 5–15 righe
ciascuno.
